# Stability Track vs UX Improvements Memo

## Background

昨日までの UX 改善（文言調整やズーム操作エリアの明確化など）において、表示の大崩れやロジックの破壊（安定性低下）を防ぐための「安定性確認トラック」をどう扱うかが課題となった。

## 結論

**UX 改修と安定性確認は異なるトラック（サイクル）として切り分ける。**

### UX 改修トラック
- **目的**: ユーザーの操作感向上、認知負荷の軽減、わかりやすさの改善。
- **検証**: 実際のブラウザ（特に Windows Chrome）での目視と操作感の確認が必須。
- **サイクル**: 仮説 → 実装 → 実機プレビュー → 微調整のループが短期間で回る。

### 安定性確認トラック
- **目的**: 既存機能のデグレ防止、ビルド成功の担保、表示崩れの検知。
- **検証**: `npm run verify` (test + build) による自動化が主。CI や Headless Chrome によるスモークテストで大崩れがないことを担保する。
- **サイクル**: PR/Commit ごとの自動チェック、またはリリース前の最終確認として機能する。

## 運用方針
1. **UX 改善時は自動テストを過信しない:** `verify` が通っていても、操作感が悪化している可能性はあるため、UX改修のExit条件には「実機確認（目視・手動操作）」を必ず含める。
2. **安定性確認は自動化に寄せる:** 基礎ロジック（時間計算など）はテストコードに任せ、人間は「使い勝手」の検証にリソースを割く。
3. **ドキュメントの分離:** `docs/development.md` に記載した通り、基礎ロジックの確認（自動）と、UI変更時の確認（手動）は明確に分けて記載・運用する。
